## C. KPI et filtres

### C.1 KPI "À finaliser" — CORRIGÉ

**Avant :**
```javascript
const aFinaliser = _myMissions.filter(m => m.status === 'delivered' || m.status === 'accepted').length;
```

**Après :**
```javascript
const aFinaliser = activeMissions.filter(m => m.status === 'delivered').length;
```

`accepted` n'est plus compté dans "À finaliser". Seul `delivered` est compté.

### C.2 KPI "Missions du jour" — CORRIGÉ

Les missions `cancelled` et `archived` sont maintenant exclues du KPI "Missions du jour" via la constante `ACTIVE_STATUSES` :

```javascript
const ACTIVE_STATUSES = ['assigned', 'accepted', 'in_progress', 'delivered', 'completed'];
const activeMissions = _myMissions.filter(m => ACTIVE_STATUSES.includes(m.status));
```

### C.3 KPI "Total missions" → "Missions actives"

Le label a été changé de "Total missions" à "Missions actives" pour refléter la sémantique correcte. Le calcul exclut `cancelled` et `archived`.

### C.4 Filtres

Filtres disponibles dans l'onglet "Mes missions" :
- Toutes
- À confirmer (`assigned`)
- Planifiées (`accepted`)
- En cours (`in_progress`)
- Livrées (`delivered`)
- Terminées (`completed`)
- **Annulées (`cancelled`)** — NOUVEAU C-2.2A

`accepted` n'est jamais mélangé avec "À finaliser".

Les filtres s'appliquent uniquement aux missions où `mission.convoyeur_id === _operatorUser.id`.

### F.4 DÉFAUT BACKEND DOCUMENTÉ — `transition_mission_status`

**Défaut identifié :** La RPC `transition_mission_status` (migration `20260809000000_phase3_b1_workflow_security_fix.sql` lignes 153-176) vérifie `is_operator()` en premier (ligne 153). Si `_is_operator = true`, le bloc `ELSIF _is_convoyeur` (ligne 165) n'est jamais atteint.

**Conséquence :** Un operator qui est aussi le convoyeur assigné ne peut PAS effectuer les transitions `accepted → in_progress` et `in_progress → delivered` car ces transitions ne sont autorisées que dans la branche `_is_convoyeur`.

**Transitions affectées :**
- `accepted → in_progress` (Démarrer) — **BLOQUÉE pour operator**
- `in_progress → delivered` (Livrer) — **BLOQUÉE pour operator**

**Transition non affectée :**
- `delivered → completed` (Finaliser) — **OK** car autorisée dans la branche `_is_operator`

**Correctif requis :** C-2.2B doit modifier la RPC pour qu'un operator qui est aussi convoyeur assigné puisse utiliser la branche `_is_convoyeur` pour les transitions terrain. Solution proposée : vérifier `_is_convoyeur` en premier, ou fusionner les autorisations.

**Aucun contournement implémenté dans C-2.2A.** Les boutons existent et déclenchent correctement la RPC — c'est la RPC qui refuse la transition.

## N. Dette reportée C-2.2B / C

### N.1 C-2.2B — Backend minimal (DÉFAUT BLOQUANT)

**Défaut :** `transition_mission_status` priorise `is_operator()` sur `is_convoyeur_for_mission()`.

**Impact :** Un operator qui est aussi le convoyeur assigné ne peut pas démarrer (`accepted → in_progress`) ni livrer (`in_progress → delivered`) une mission. Seul `Finaliser` (`delivered → completed`) fonctionne car cette transition est autorisée dans la branche `_is_operator`.

**Correctif :** Modifier la RPC pour qu'un operator qui est aussi convoyeur assigné puisse utiliser les transitions de la branche `_is_convoyeur`. Solutions possibles :
1. Vérifier `_is_convoyeur` en premier (avant `_is_operator`)
2. Fusionner les autorisations : si `_is_operator AND _is_convoyeur`, autoriser l'union des transitions des deux branches
3. Ajouter les transitions convoyeur à la branche operator

**Autres items C-2.2B :**
- RLS `mission_events` explicite pour operator (clarté, pas critique car l'accès implicite fonctionne)
- RPC `get_mission_contact` pour le téléphone de livraison au convoyeur assigné
- Conversion `heure_depart` de `text` vers `time` (tri temporel fiable)
