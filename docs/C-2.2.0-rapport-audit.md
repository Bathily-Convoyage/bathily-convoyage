### B.3 KPI "À finaliser" — analyse

**Code actuel** (`dashboard-operator.html` ligne 808) :
```javascript
const aFinaliser = _myMissions.filter(m => m.status === 'delivered' || m.status === 'accepted').length;
```

**Verdict : INCORRECT métier.**
- `accepted` = mission acceptée, pas encore démarrée → c'est une mission "à venir" ou "planifiée"
- `delivered` = véhicule livré, en attente de finalisation administrative → c'est une vraie mission "à finaliser"
- Combiner ces deux statuts n'a pas de sens métier
- `accepted` est déjà compté dans "Prochaines missions" (lignes 817-819) → double comptage

**Recommandation :** `aFinaliser` devrait être uniquement `status === 'delivered'`.

### B.4 Missions annulées / archivées

- **Filtres :** Aucun filtre `cancelled` ou `archived` dans dashboard-operator.html
- **Visibilité :** Visibles dans "Toutes" (pas de filtre de statut)
- **KPI Total :** Inclut cancelled + archived
- **KPI Missions du jour :** Inclut cancelled + archived si date = aujourd'hui
- **Recommandation :** Exclure cancelled/archived des KPIs "du jour" et "total actif" ; ajouter filtre "Annulées"

### D.5 Comportement pour un operator interne

**L'operator avec une ligne `convoyeurs` peut-il lire `mission_events` ?**

**OUI, implicitement.** La policy `mission_events_convoyeur_select_b2` vérifie `convoyeurs.auth_user_id = auth.uid()`. Un operator qui a une ligne `convoyeurs` avec son `auth_user_id` satisfait cette condition pour les missions où il est le convoyeur assigné.

**Cependant :**
- Pas de policy explicite `is_operator()` — l'accès est implicite via la policy convoyeur
- Un operator SANS ligne `convoyeurs` ne peut PAS lire `mission_events`
- L'accès est limité aux missions où `convoyeur_id` correspond à la ligne `convoyeurs` de l'operator

### D.6 Comportement pour un convoyeur assigné

Identique à l'operator avec ligne convoyeurs — la policy `mission_events_convoyeur_select_b2` s'applique.

### D.7 Immutabilité

**Append-only strict** — trigger `mission_events_protect` bloque UPDATE et DELETE pour tous (y compris postgres via SECURITY INVOKER). Source : lignes 78-94.
