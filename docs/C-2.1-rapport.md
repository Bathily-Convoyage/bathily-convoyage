## 1. Objectif

Finaliser l'Espace Missions interne pour les opérateurs Bathily-Convoyage, distinct du Dashboard Admin et du Dashboard Convoyeur (externe). L'Espace Missions est l'interface personnelle d'exécution d'un opérateur interne : missions du jour, à venir, en cours, à finaliser, détails, et accès aux outils terrain (bon de mission, état des lieux, GPS, signature, incidents, dépenses).

Les convoyeurs externes restent **hors périmètre C-2**. Le feature flag `external_convoyeurs_enabled` doit rester `false`.

## 2. Décisions d'architecture appliquées

### Décision #1 — Distinction interne/externe via `is_internal_user()`

Les RPC existants (`respond_mission_assignment`, `validate_mission_edl`, `authorize_gps_session`, `record_gps_position`) utilisent déjà `is_convoyeur_for_mission()` **ET** `(is_internal_user() OR external_convoyeurs_enabled())`. Un operator avec une ligne `convoyeurs` est reconnu comme interne via `is_internal_user()` (qui appelle `is_operator()`).

**Conclusion :** Aucune modification des RPC n'était nécessaire. La distinction interne/externe est déjà correctement implémentée côté backend.

### Décision #2 — `app_settings` UPDATE restreint à `is_admin()`

La policy `app_settings_update_b3v` accordait l'UPDATE à `(is_admin() OR is_operator())`. Un operator pouvait théoriquement modifier `external_convoyeurs_enabled` et activer les convoyeurs externes, violant l'invariant absolu du projet.

**Correction appliquée :** Migration `20260809000011_phase3_c21_app_settings_admin_only.sql` qui :
- Conserve SELECT pour `is_admin() OR is_operator()` (lecture interne nécessaire au feature flag)
- Restreint UPDATE à `is_admin()` uniquement
- Inclut des vérifications transactionnelles (RLS activée, policy créée, ancienne policy supprimée, flag présent)

### Décision #3 — `dashboard-operator.html` comme page autonome

Création d'une page HTML autonome `dashboard-operator.html`, distincte de `dashboard-convoyeur.html` et `dashboard-admin.html`. Elle ne réutilise pas le code du dashboard convoyeur externe (qui contient candidatures, communauté, gamification, badges, retours possibles).

## 4. `dashboard-operator.html` — Architecture

### 4.1 Authentification

**Login :**
1. `signInWithPassword` (Supabase Auth)
2. RPC `is_operator()` → doit retourner `true` (sinon : refus propre, signOut)
3. Lecture ligne `convoyeurs` par `auth_user_id = session.user.id` (RLS `convoyeurs_select_own_or_admin` autorise `auth_user_id = auth.uid()`)
4. Si pas de ligne convoyeurs → erreur "profil exécutant non configuré" (pas de création automatique, pas de contournement de RPC)
5. Si `banned === true` → refus

**Vérification session au chargement :**
- Revalide systématiquement `is_operator()` côté serveur au chargement (contrairement à `dashboard-convoyeur.html` qui se fie à `sessionStorage`)
- Évite qu'une session admin/client/convoyeur externe persistée ne contourne le garde-frontière
- Si session valide mais pas operator → n'appelle pas `signOut` (l'utilisateur peut avoir une autre session valide pour un autre espace), mais refuse l'accès à l'Espace Missions

### 4.2 Chargement des missions

- RLS `missions_select_b3` autorise `is_operator()` à lire toutes les missions
- **MAIS** l'Espace Missions est une interface personnelle d'exécution : le frontend filtre strictement `convoyeur_id === _operatorUser.id`
- Aucune requête vers `candidatures`, `reseau_posts`, `reseau_comments`, `badges`, `convoyeur_badges`, `convoyeur_candidatures`, ou missions disponibles externes

### 4.3 Outils terrain accessibles

- **Bon de mission** : `bon-de-mission.html?id=${m.id}` (avec garde d'auth)
- **État des lieux** : `etat-des-lieux.html?mission_id=${m.id}&type=depart` (avec garde d'auth)
- **GPS** : `gps-emitter.html?id=${m.id}&ref=...&route=...&vehicle=...` (uniquement si `status === 'in_progress'`)

### 4.4 Actions opérationnelles

- **Accepter/Refuser mission** : via RPC `respond_mission_assignment` (existante, sécurisée)
- **Filtres** : Toutes / À confirmer / Planifiées / En cours / Livrées / Terminées

### 4.5 KPIs affichés

- Missions du jour
- En cours
- À finaliser (delivered + accepted)
- Total missions assignées

## 5. Gardes d'authentification ajoutées

### 5.1 `bon-de-mission.html`

**Avant :** Absence de garde d'authentification frontend avant tentative de lecture. Défense en profondeur insuffisante côté frontend : mauvaise UX et erreurs potentielles avant résolution de l'accès. **Aucune fuite PII anonyme démontrée** puisque la RLS backend `missions_select_b3` restait active et bloquait les lectures anonymes.

**Après :** Avant toute lecture de données mission :
1. `sb.auth.getSession()` — si pas de session → refus propre (page "Accès réservé")
2. RPC `is_operator()` OU RPC `is_convoyeur_for_mission({ p_mission_id, p_user_id })` — si aucun des deux → refus propre
3. Only then : lecture de la mission

La sécurité réelle reste assurée par la RLS `missions_select_b3` côté backend ; la garde frontend est une barrière UX + défense en profondeur + empêche l'affichage de messages bruts Supabase au visiteur.

### 5.2 `etat-des-lieux.html`

**Avant :** Authentification partielle (uniquement sur validation via `validate_mission_edl`). Absence de garde d'authentification frontend au chargement, avant tentative de lecture. Défense en profondeur insuffisante côté frontend. **Aucune fuite PII anonyme démontrée** puisque la RLS backend restait active.

**Après :** Garde d'authentification identique à `bon-de-mission.html`, appliquée au chargement avant toute lecture de données mission.

## 7. Contradiction `transition_mission_status` — résolution

**Rapport C-2.0 :** Indiquait que `transition_mission_status` autorisait admins/operators pour des transitions globales, mais un test impliquait un refus pour la mission d'un autre operator.

**Analyse SQL :** La RPC autorise `_is_admin OR _is_operator` à performer un ensemble de transitions sur **n'importe quelle mission** (available→assigned, assigned→cancelled, delivered→completed, etc.), tandis que `_is_convoyeur` est restreint à ses missions assignées.

**Conclusion :** Comportement intentionnel. Operator = gestionnaire interne (peut gérer toutes les missions), convoyeur = exécutant (restreint à ses missions). Documenté sans modification.
